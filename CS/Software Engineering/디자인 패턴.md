# 디자인 패턴이란?
- 소프트웨어 설계에서 **자주 발생하는 문제** 에 대한 **재사용 가능한 해결 방법** 이다.
- 검증된 설계를 공유함으로써 코드의 **재사용성, 유지보수성, 확장성** 을 향상시킨다.
- 1994 년 **GoF (Gang of Four)** 가 정리한 23 가지 패턴이 가장 유명하다.

<br><br><br>

# GoF 디자인 패턴
- **Creational Pattern (생성 패턴)** : 객체 생성과 관련된 패턴
- **Structural Pattern (구조 패턴)** : 클래스와 객체의 구성과 관련된 패턴
- **Behavioral Pattern (행위 패턴)** : 객체 간 상호작용과 책임 분배와 관련된 패턴

<br><br><br>

# 생성 패턴 (Creational)

### 1. Singleton
- 클래스의 인스턴스가 **오직 하나만** 존재하도록 보장한다.
- 전역적으로 접근 가능한 단일 객체를 제공.
- 예 : 설정 관리, 로깅, DB 연결 풀

```swift
class Logger {
    static let shared = Logger()
    private init() {}
    func log(_ message: String) { print(message) }
}
```

### 2. Factory Method
- 객체 생성 로직을 **서브클래스** 에 위임한다.
- 어떤 객체를 만들지 결정하는 책임을 분리.

```swift
protocol Transport { func deliver() }
class Truck: Transport { func deliver() { print("Deliver by truck") } }
class Ship: Transport { func deliver() { print("Deliver by ship") } }

class TransportFactory {
    func create(type: String) -> Transport {
        switch type {
        case "truck": return Truck()
        case "ship": return Ship()
        default: fatalError()
        }
    }
}
```

### 3. Abstract Factory
- 관련된 여러 객체를 **묶어서** 생성하는 인터페이스를 제공한다.
- 구체 클래스에 의존하지 않고 객체 계열을 생성할 수 있다.

### 4. Builder
- 복잡한 객체를 **단계별로** 생성한다.
- 같은 생성 과정으로 다른 표현의 객체를 만들 수 있다.

### 5. Prototype
- 기존 인스턴스를 **복제** 해 새 인스턴스를 만든다.
- 객체 생성 비용이 클 때 유용.

<br><br><br>

# 구조 패턴 (Structural)

### 1. Adapter
- **호환되지 않는** 인터페이스를 가진 객체들을 함께 동작하게 해준다.
- 기존 클래스의 인터페이스를 다른 인터페이스로 **변환** 한다.

```swift
// iOS 의 UITableViewDataSource 도 일종의 Adapter 역할
```

### 2. Bridge
- 추상화와 구현을 분리해 **독립적으로 변경** 가능하게 한다.

### 3. Composite
- 객체를 트리 구조로 구성해 **부분-전체** 계층을 표현한다.
- 단일 객체와 복합 객체를 동일하게 다룰 수 있다.
- 예 : UIView 의 계층 구조

### 4. Decorator
- 기존 객체를 **동적으로 확장** 한다.
- 상속의 대안으로, 기능을 유연하게 추가할 수 있다.

### 5. Facade
- 복잡한 서브시스템에 대한 **통합된 단순 인터페이스** 를 제공한다.
- 서브시스템의 복잡도를 숨긴다.

### 6. Proxy
- 다른 객체에 대한 **대리자** 를 제공해 접근을 제어한다.
- Lazy Initialization, Access Control, Caching 등에 사용.

# 행위 패턴 (Behavioral)

### 1. Observer
- 객체의 상태 변화에 대해 **관심 있는 객체들에게 알림** 을 보낸다.
- 예 : NotificationCenter, KVO, Combine Publisher

```swift
// Swift Combine 의 Observer 패턴
class Store: ObservableObject {
    @Published var count = 0
}
```

### 2. Strategy
- 알고리즘을 **캡슐화** 해서 **런타임에 교체** 할 수 있게 한다.
- if-else 를 제거하고 OCP 를 준수.

```swift
protocol PaymentStrategy { func pay(_ amount: Double) }
class CreditCard: PaymentStrategy { ... }
class PayPal: PaymentStrategy { ... }

class Cart {
    var payment: PaymentStrategy
    init(payment: PaymentStrategy) { self.payment = payment }
    func checkout(_ amount: Double) { payment.pay(amount) }
}
```

### 3. Command
- 요청을 **객체로 캡슐화** 해 매개변수화하고 Undo, Logging 등을 가능하게 한다.

### 4. Template Method
- 알고리즘의 **골격** 은 상위 클래스에서 정의하고, 세부 단계는 하위 클래스에서 구현한다.

### 5. Iterator
- 컬렉션의 내부 구조를 노출하지 않고 **순회** 할 수 있는 방법을 제공.
- Swift 의 `IteratorProtocol`, `Sequence` 가 이에 해당.

### 6. State
- 객체의 **내부 상태** 에 따라 행동이 달라지도록 한다.
- 상태를 객체로 분리해 관리.

### 7. Mediator
- 객체 간 직접 통신을 피하고 **중재자** 를 통해 통신한다.
- 결합도를 낮춘다. 예 : Coordinator 패턴

### 8. Chain of Responsibility
- 요청을 처리할 수 있는 객체들을 **체인** 으로 연결해 순차적으로 전달.
- 예 : UIResponder Chain

### 9. Visitor
- 자료구조와 처리를 분리해 자료구조에 다양한 연산을 수행할 수 있게 한다.

### 10. Memento
- 객체의 **상태를 저장** 해 나중에 복원할 수 있게 한다.
- Undo 기능 구현.

# iOS 에서 자주 쓰는 패턴

### MVC / MVVM / VIPER
- UI 아키텍처 패턴. `/Patterns/` 폴더의 MVC, MVVM 문서 참고.

### Delegate Pattern
- **일대일** 로 어떤 작업을 다른 객체에 위임한다.
- `UITableViewDelegate`, `UITextFieldDelegate` 등 iOS 에서 가장 널리 사용되는 패턴.

### Singleton
- `UIApplication.shared`, `UserDefaults.standard`, `FileManager.default` 등.

### Observer
- `NotificationCenter`, `KVO`, `Combine`, `@Published`.

### Coordinator
- 화면 전환 로직을 ViewController 에서 분리. Mediator 패턴의 응용.

### Builder
- `URLRequest`, `DateComponents` 등을 단계별로 구성.

# 면접 예상 질문
- **Q. 디자인 패턴을 사용하면 어떤 이점이 있나요?**
  - 검증된 설계를 재사용할 수 있어 **개발 시간이 단축** 되고, 공통 용어로 **의사소통이 쉬워지며**, 유지보수와 확장이 용이한 코드를 작성할 수 있습니다. 또한 같은 패턴을 아는 개발자들끼리 빠르게 코드를 이해할 수 있습니다.

- **Q. Singleton 패턴의 단점은?**
  - 전역 상태를 만들어 **의존성 추적이 어려워지고** , **단위 테스트가 어려워집니다** (Mock 으로 교체 불가). 또한 멀티스레드 환경에서 동기화 이슈가 발생할 수 있어 주의해야 하며, Swift 에서는 `static let` 으로 스레드 안전하게 생성할 수 있습니다.

- **Q. Strategy 패턴은 언제 사용하나요?**
  - 같은 목적의 알고리즘이 여러 개 있고, **런타임에 교체** 해야 할 때 사용합니다. 예를 들어 결제 방식(카드/페이팔/카카오페이) 을 교체하거나 정렬 방식을 변경할 때 적합합니다. if-else 분기를 제거해 OCP 를 준수하는 설계가 됩니다.

- **Q. Delegate 와 Observer 패턴의 차이는?**
  - Delegate 는 **1:1** 통신이고 동기적이며 특정 객체에게 책임을 위임하는 방식입니다. Observer 는 **1:N** 통신으로 여러 객체가 상태 변화를 구독할 수 있고, 보통 비동기입니다. iOS 에서는 NotificationCenter, Combine 이 Observer 패턴의 예입니다.

- **Q. Swift 에서 Factory 패턴이 필요한가요?**
  - Swift 는 정적 팩토리 메서드와 열거형 기반 초기화를 자주 사용하므로 전통적인 Factory Method 패턴이 덜 필요합니다. 하지만 **객체 생성 로직이 복잡** 하거나 **생성 타입이 조건에 따라 결정** 되어야 할 때는 여전히 유용합니다.
