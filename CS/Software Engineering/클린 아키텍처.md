# Clean Architecture 란?
- **Robert C. Martin (Uncle Bob)** 이 제안한 소프트웨어 아키텍처 원칙이다.
- 핵심 목표는 **관심사의 분리 (Separation of Concerns)** 를 통해 시스템을 유지보수 가능하고 테스트하기 쉽게 만드는 것이다.
- 프레임워크, UI, 데이터베이스 등의 **외부 요소에 독립적인** 비즈니스 로직을 구성한다.
- Hexagonal Architecture, Onion Architecture 등과 공통된 사상을 가진다.

### 핵심 원칙
1. **프레임워크 독립성** : 특정 프레임워크에 의존하지 않는다.
2. **테스트 용이성** : 비즈니스 규칙을 UI, DB, 서버 없이 테스트할 수 있다.
3. **UI 독립성** : UI 를 변경해도 비즈니스 로직에 영향을 주지 않는다.
4. **데이터베이스 독립성** : DB 를 교체해도 비즈니스 로직에 영향을 주지 않는다.
5. **외부 에이전시 독립성** : 비즈니스 규칙은 외부 세계에 대해 아무것도 알지 못한다.

<br><br><br>

# 의존성 규칙 (Dependency Rule)
- Clean Architecture 의 **가장 핵심적인 규칙** 이다.
- **소스 코드의 의존성은 항상 안쪽 (고수준) 으로만 향해야 한다.**
- 안쪽 원 (Entity, Use Case) 은 바깥쪽 원 (Framework, UI) 에 대해 아무것도 알지 못한다.
- 바깥쪽에서 선언한 이름 (함수, 클래스, 변수 등) 을 안쪽에서 언급해서는 안 된다.

```
[Framework & Driver] → [Interface Adapter] → [Use Case] → [Entity]
         ↑                     ↑                   ↑           ↑
       바깥쪽                                                안쪽
    (저수준, 세부사항)                                  (고수준, 정책)
```

<br><br><br>

# 계층 구조

### 1. Entity (엔티티)
- **비즈니스 규칙** 을 캡슐화한다.
- 가장 안쪽에 위치하며, 외부 변화에 의해 변경되지 않는다.
- 기업 수준의 비즈니스 규칙 (Enterprise Business Rules) 을 포함한다.

```swift
struct User {
    let id: String
    let name: String
    let email: String
    
    func isValidEmail() -> Bool {
        return email.contains("@") && email.contains(".")
    }
}
```

### 2. Use Case (유스케이스)
- **애플리케이션의 비즈니스 규칙** 을 포함한다.
- Entity 를 사용해 시스템의 동작을 구현한다.
- UI 나 DB 가 어떻게 동작하는지 알지 못한다.

```swift
protocol UserRepository {
    func fetchUser(id: String) async throws -> User
    func saveUser(_ user: User) async throws
}

class GetUserUseCase {
    private let repository: UserRepository
    
    init(repository: UserRepository) {
        self.repository = repository
    }
    
    func execute(userId: String) async throws -> User {
        return try await repository.fetchUser(id: userId)
    }
}
```

### 3. Interface Adapter (인터페이스 어댑터)
- Use Case 와 Entity 의 데이터를 **외부 에이전시에 맞는 형식으로 변환** 한다.
- **Presenter, ViewModel, Controller, Gateway** 등이 이 계층에 속한다.
- DB 의 데이터 형식을 Use Case 에 맞게 변환하거나, Use Case 의 결과를 UI 에 맞게 변환한다.

```swift
class UserViewModel: ObservableObject {
    @Published var userName: String = ""
    @Published var errorMessage: String?
    
    private let getUserUseCase: GetUserUseCase
    
    init(getUserUseCase: GetUserUseCase) {
        self.getUserUseCase = getUserUseCase
    }
    
    func loadUser(id: String) async {
        do {
            let user = try await getUserUseCase.execute(userId: id)
            await MainActor.run {
                self.userName = user.name
            }
        } catch {
            await MainActor.run {
                self.errorMessage = error.localizedDescription
            }
        }
    }
}
```

### 4. Framework & Driver (프레임워크와 드라이버)
- **가장 바깥쪽** 계층이며 세부사항이다.
- DB, 웹 프레임워크, UI 프레임워크 등의 구체적인 구현이 위치한다.
- 안쪽 계층과 통신하기 위한 **접착 코드 (Glue Code)** 를 포함한다.

```swift
class UserRepositoryImpl: UserRepository {
    func fetchUser(id: String) async throws -> User {
        // 실제 네트워크 호출 또는 DB 조회
        let url = URL(string: "https://api.example.com/users/\(id)")!
        let (data, _) = try await URLSession.shared.data(from: url)
        let dto = try JSONDecoder().decode(UserDTO.self, from: data)
        return User(id: dto.id, name: dto.name, email: dto.email)
    }
    
    func saveUser(_ user: User) async throws {
        // DB 저장 구현
    }
}
```

# 의존성 역전 원칙 (DIP)
- 의존성 규칙을 지키기 위해 **의존성 역전 원칙 (Dependency Inversion Principle)** 을 사용한다.
- 고수준 모듈 (Use Case) 이 저수준 모듈 (Repository 구현체) 에 직접 의존하지 않는다.
- 대신 **추상화 (Protocol / Interface)** 에 의존한다.

```
[Use Case] → [UserRepository Protocol] ← [UserRepositoryImpl]
  (고수준)        (추상화, 경계)              (저수준, 구현)
```

- Use Case 는 `UserRepository` **프로토콜** 에만 의존한다.
- `UserRepositoryImpl` 은 그 프로토콜을 구현 (conform) 한다.
- 이를 통해 **소스 코드의 의존성과 제어 흐름의 방향이 반대** 가 된다.

# 의존성 주입 (DI)
- **Dependency Injection** 은 객체가 필요로 하는 의존성을 **외부에서 주입** 하는 패턴이다.
- Clean Architecture 에서 의존성 역전을 실현하는 구체적인 방법이다.

### 주입 방식

#### 1. 생성자 주입 (Constructor Injection) — 가장 권장됨
```swift
class GetUserUseCase {
    private let repository: UserRepository
    
    init(repository: UserRepository) {
        self.repository = repository
    }
}
```

#### 2. 프로퍼티 주입 (Property Injection)
```swift
class GetUserUseCase {
    var repository: UserRepository!
}
```

#### 3. 메서드 주입 (Method Injection)
```swift
class GetUserUseCase {
    func execute(userId: String, repository: UserRepository) async throws -> User {
        return try await repository.fetchUser(id: userId)
    }
}
```

### DI 의 장점
- **테스트 용이성** : Mock 객체를 쉽게 주입해 단위 테스트를 할 수 있다.
- **결합도 감소** : 구체적인 구현이 아닌 추상화에 의존하므로 교체가 쉽다.
- **유연성** : 런타임에 다른 구현체를 주입할 수 있다.

# iOS 아키텍처 패턴 비교

| 패턴 | 구조 | 특징 | 적합한 규모 |
|---|---|---|---|
| **MVC** | Model-View-Controller | Apple 기본 패턴, Massive VC 문제 | 소규모 |
| **MVP** | Model-View-Presenter | View 와 Model 분리, Presenter 가 중재 | 소~중규모 |
| **MVVM** | Model-View-ViewModel | 데이터 바인딩, Reactive 에 적합 | 중규모 |
| **VIPER** | View-Interactor-Presenter-Entity-Router | 역할이 명확히 분리, 파일이 많음 | 대규모 |
| **RIBs** | Router-Interactor-Builder (+ optional View) | Uber 개발, 비즈니스 로직 중심 트리 | 대규모 |
| **TCA** | The Composable Architecture | SwiftUI + Combine, 단방향 데이터 흐름 | 중~대규모 |

### Clean Architecture 와의 관계
- Clean Architecture 는 **특정 패턴이 아닌 원칙** 이다.
- MVVM, VIPER, RIBs 등은 Clean Architecture 의 원칙을 구현하는 **구체적인 방법** 이 될 수 있다.
- 예를 들어 MVVM + Clean Architecture 구조에서는 :
  - **Entity** : 도메인 모델
  - **Use Case** : 비즈니스 로직
  - **ViewModel** : Interface Adapter (Use Case 결과를 View 에 맞게 변환)
  - **View** : UI (Framework & Driver)
  - **Repository** : 데이터 접근 (Framework & Driver)

# 면접 예상 질문
- **Q. Clean Architecture 란 무엇인가요?**
  - Robert C. Martin 이 제안한 아키텍처 원칙으로, **관심사의 분리** 를 통해 비즈니스 로직을 프레임워크, UI, DB 등의 외부 요소로부터 독립시키는 것을 목표로 합니다. 핵심은 **의존성 규칙** 으로, 소스 코드의 의존성이 항상 안쪽 (고수준) 으로만 향해야 합니다.

- **Q. 의존성 규칙이 왜 중요한가요?**
  - 의존성 규칙을 지키면 **비즈니스 로직이 외부 변화에 영향받지 않습니다**. DB 를 교체하거나 UI 프레임워크를 변경해도 핵심 로직은 그대로 유지됩니다. 또한 비즈니스 로직을 외부 의존성 없이 **독립적으로 테스트** 할 수 있어 코드 품질이 향상됩니다.

- **Q. 의존성 주입 (DI) 이란 무엇이고 왜 사용하나요?**
  - 객체가 필요로 하는 의존성을 **내부에서 직접 생성하지 않고 외부에서 전달받는** 패턴입니다. 이를 통해 구체적인 구현이 아닌 **추상화 (Protocol) 에 의존** 하게 되어 결합도가 낮아지고, Mock 객체 주입으로 **테스트가 용이** 해집니다. 생성자 주입이 가장 권장됩니다.

- **Q. MVVM 과 Clean Architecture 의 관계는?**
  - MVVM 은 **UI 계층의 패턴** 이고, Clean Architecture 는 **전체 시스템의 아키텍처 원칙** 입니다. 둘을 함께 사용할 수 있으며, 이 경우 ViewModel 은 Clean Architecture 의 Interface Adapter 계층에 위치하고, Use Case 를 호출해 비즈니스 로직을 실행하고 그 결과를 View 에 맞게 변환하는 역할을 합니다.

- **Q. iOS 에서 Clean Architecture 를 적용하면 어떤 장단점이 있나요?**
  - **장점** : 비즈니스 로직을 UIKit/SwiftUI 없이 테스트할 수 있고, 역할이 명확히 분리되어 협업이 쉽습니다. DB 나 네트워크 라이브러리 교체 시 영향 범위가 최소화됩니다. **단점** : 파일 수가 많아지고, 작은 프로젝트에서는 오버엔지니어링이 될 수 있습니다. 계층 간 데이터 변환 코드 (DTO → Entity) 가 반복될 수 있습니다.
