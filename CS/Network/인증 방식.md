# 인증과 인가
- **Authentication (인증)** : 사용자가 **누구인지** 확인하는 과정 (로그인)
- **Authorization (인가)** : 사용자가 **어떤 권한** 을 가지는지 확인하는 과정

<br><br><br>

# Cookie
- 서버가 클라이언트에 저장하는 **작은 데이터 조각** 이다.
- 브라우저가 자동으로 요청 시 서버에 함께 전송한다.
- Key-Value 쌍으로 저장된다.

### 주요 속성
- **Expires / Max-Age** : 만료 시간
- **Domain / Path** : 쿠키가 전송될 도메인/경로
- **Secure** : HTTPS 에서만 전송
- **HttpOnly** : JavaScript 접근 차단 (XSS 방어)
- **SameSite** : Cross-Site 요청에서 쿠키 전송 정책 (CSRF 방어)

### 단점
- 크기 제한 (도메인당 4KB)
- 매 요청마다 전송되어 트래픽 증가
- 보안에 취약 (탈취 가능)

<br><br><br>

# Session
- 서버가 사용자 정보를 **서버 메모리/DB 에 저장** 하고, 식별자인 **Session ID** 만 클라이언트에 전달하는 방식이다.
- 클라이언트는 Session ID 를 **Cookie** 로 저장해 요청 시마다 전송한다.

### 동작 과정

```
1. Client → Server : 로그인 요청 (ID / PW)
2. Server : 사용자 정보 확인 후 Session 생성 (서버 저장)
3. Server → Client : Session ID 를 쿠키로 전달
4. Client → Server : 이후 요청 시 Session ID 쿠키 전송
5. Server : Session ID 로 사용자 식별
```

### 장점
- 사용자 정보가 서버에 저장되어 **보안에 유리**
- 서버에서 언제든 Session 을 강제 만료시킬 수 있음

### 단점
- 서버가 모든 사용자 세션을 저장해야 해 **메모리 부담**
- **Scale-Out 이 어렵다** (여러 서버 간 Session 공유 필요)
- 해결책 : Redis 같은 중앙 저장소 사용, Sticky Session 사용

<br><br><br>

# Token 기반 인증
- 서버가 사용자 정보를 담은 **토큰** 을 발급해 클라이언트가 저장하는 방식.
- 서버는 Session 을 저장하지 않아도 되므로 **Stateless** 하다.

### 동작 과정

```
1. Client → Server : 로그인 요청
2. Server : 사용자 확인 후 Token 발급 (서명 포함)
3. Server → Client : Token 전달
4. Client : Token 을 저장 (LocalStorage / Cookie)
5. Client → Server : Authorization 헤더에 Token 포함해 요청
6. Server : Token 검증 후 요청 처리
```

<br><br><br>

# JWT (JSON Web Token)
- Token 기반 인증의 대표적인 구현체이다.
- 3 부분으로 구성된 문자열이다 : `Header.Payload.Signature`

### 구조

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.    ← Header
eyJzdWIiOiIxMjMiLCJuYW1lIjoiUmFjY29vbiJ9. ← Payload
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c ← Signature
```

### 1. Header
```json
{
    "alg": "HS256",
    "typ": "JWT"
}
```

### 2. Payload
- **Claims** (사용자 정보, 만료 시간 등) 이 담긴다.
```json
{
    "sub": "user123",
    "name": "Raccoon",
    "exp": 1735689600
}
```

### 3. Signature
- Header 와 Payload 를 Secret Key 로 서명한 값.
- 토큰의 **무결성** 을 보장한다.

### 장점
- **Stateless** : 서버가 Session 을 저장하지 않아도 됨
- Scale-Out 이 용이
- 자체적으로 사용자 정보를 포함해 별도 DB 조회 불필요

### 단점
- **탈취 시 대응이 어렵다** (서버가 토큰을 강제 만료시키기 어려움)
- Payload 는 **암호화가 아닌 Base64 인코딩** 이므로 누구나 볼 수 있음 → 민감 정보 넣지 말 것
- 토큰 크기가 커 네트워크 부담

### Access Token & Refresh Token
- **Access Token** : 실제 API 요청에 사용, **짧은 만료 시간** (보통 15 분 ~ 1 시간)
- **Refresh Token** : Access Token 재발급에 사용, **긴 만료 시간** (보통 2 주 ~ 1 달)
- Access Token 이 탈취되어도 빠르게 만료되어 피해를 최소화할 수 있다.

<br><br><br>

# OAuth 2.0
- **제 3 자 서비스** 의 리소스에 접근할 수 있는 권한을 위임하는 표준 프로토콜이다.
- 예 : "Google 계정으로 로그인", "GitHub 계정으로 로그인"
- 사용자가 서비스에 직접 비밀번호를 제공하지 않고도 인증/인가할 수 있다.

### 구성 요소
- **Resource Owner** : 사용자
- **Client** : 서비스를 제공하는 애플리케이션
- **Authorization Server** : 인증 서버 (예 : Google)
- **Resource Server** : 보호된 자원을 가진 서버 (예 : Google Drive)

### Authorization Code Grant (가장 일반적)

```
1. Client → Auth Server : 사용자 승인 요청
2. 사용자 동의
3. Auth Server → Client : Authorization Code 발급
4. Client → Auth Server : Code + Client Secret 으로 Access Token 요청
5. Auth Server → Client : Access Token 발급
6. Client → Resource Server : Access Token 으로 리소스 접근
```

<br><br><br>

# 각 방식의 비교

| 구분 | Session | JWT | OAuth 2.0 |
|---|---|---|---|
| 저장 위치 | 서버 | 클라이언트 | 서드파티 서버 |
| Stateful | Stateful | Stateless | Stateless |
| Scale-Out | 어려움 | 쉬움 | 쉬움 |
| 토큰 만료 제어 | 쉬움 | 어려움 | 쉬움 |
| 용도 | 일반 로그인 | API 인증 | 제 3 자 인증 위임 |

# 면접 예상 질문
- **Q. Session 과 JWT 중 무엇을 사용해야 하나요?**
  - 상황에 따라 다릅니다. 보안이 중요하고 세션 제어 (강제 로그아웃 등) 가 필요하면 Session 이 유리하고, Scale-Out 이 필요하고 모바일/API 를 많이 사용하는 서비스라면 JWT 가 유리합니다. 실무에서는 JWT 와 Refresh Token 을 조합해 단점을 보완하는 경우가 많습니다.

- **Q. JWT 가 탈취되면 어떻게 대응하나요?**
  - JWT 는 Stateless 이기 때문에 서버에서 강제로 만료시키기 어렵습니다. 대응 방법으로는 (1) **Access Token 의 만료 시간을 짧게** 설정하고 (2) **Refresh Token 을 DB 에 저장** 해 필요 시 무효화하며 (3) **Token Blacklist** 를 Redis 에 유지하는 방법이 있습니다.

- **Q. Cookie 의 HttpOnly 와 Secure 옵션은 무엇인가요?**
  - **HttpOnly** 는 JavaScript 에서 쿠키에 접근할 수 없게 해 **XSS 공격을 방어** 합니다. **Secure** 는 HTTPS 에서만 쿠키를 전송하도록 해 **중간자 공격 (MITM)** 을 방지합니다. 인증용 쿠키에는 두 옵션을 모두 적용하는 것이 권장됩니다.

- **Q. OAuth 2.0 의 역할은?**
  - 사용자가 비밀번호를 제 3 자 서비스에 제공하지 않고도 권한을 위임할 수 있게 해주는 프로토콜입니다. 예를 들어 "카카오 로그인" 을 통해 사용자가 직접 카카오에 인증하고, 서비스는 카카오가 발급한 Access Token 으로 사용자 정보에 접근할 수 있습니다.

- **Q. JWT 의 Payload 에 민감한 정보를 넣어도 되나요?**
  - 아닙니다. JWT 의 Payload 는 **Base64 인코딩** 일 뿐 **암호화가 아니므로** 누구나 디코딩해 볼 수 있습니다. 비밀번호, 주민번호 등 민감 정보는 절대 넣으면 안 되며, 필요하다면 JWE (JSON Web Encryption) 를 사용해 암호화해야 합니다.
